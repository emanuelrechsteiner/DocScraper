## Architecture Decision Records (ADRs)

### ADR-001 — API Framework: FastAPI

| Field | Value |
|-------|-------|
| **Date** | 2026-03-22 |
| **Status** | Accepted |
| **Deciders** | Brainstorm pipeline |

**Context:** Parsify wraps existing async Python scraping engines in a REST API. The framework must support native async/await (for crawl4ai), auto-generate OpenAPI documentation, and handle long-running background jobs.

**Decision:** FastAPI with Pydantic v2 for request/response validation. Auto-generated OpenAPI docs at `/docs` (Swagger) and `/redoc`.

**Alternatives Considered:**

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Django REST Framework | Mature, large ecosystem, admin panel | Synchronous by default, heavy ORM coupling, slower for pure API | Overkill for API-only service, async support is bolted on |
| Flask + Flask-RESTX | Simple, lightweight, familiar | No native async, manual validation, less type safety | Our engines are async — sync framework would negate performance |

**Consequences:**
- Automatic OpenAPI spec generation from Pydantic models
- Native async support matches existing engine architecture
- Smaller ecosystem than Django — less pre-built middleware
- Pydantic v2 has breaking changes from v1 — must use v2 patterns

**Revisit When:**
- If we need a full admin panel → consider Django admin alongside FastAPI
- If performance requirements demand non-Python → consider Go/Rust

### ADR-002 — Database: PostgreSQL + SQLAlchemy 2.0

| Field | Value |
|-------|-------|
| **Date** | 2026-03-22 |
| **Status** | Accepted |
| **Deciders** | Brainstorm pipeline |

**Context:** Need to store user accounts, API keys, job state, usage records, and subscription data. Must support async operations and migrations.

**Decision:** PostgreSQL with SQLAlchemy 2.0 (async) and Alembic for migrations.

**Alternatives Considered:**

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| SQLModel | Cleaner syntax, built on SQLAlchemy + Pydantic | Less mature, limited migration support, fewer advanced features | Too new for production reliance, harder to debug |
| Tortoise ORM | Async-first, Django-like | Smaller community, fewer integrations | SQLAlchemy is more battle-tested for production |
| MongoDB | Flexible schema, good for document storage | Poor for relational data (users ↔ keys ↔ jobs), no ACID guarantees across collections | Our data is highly relational |

**Consequences:**
- SQLAlchemy 2.0 async requires careful session management
- Alembic auto-generates migrations from model changes
- PostgreSQL is available on all deployment platforms
- More boilerplate than SQLModel, but more production-proven

**Revisit When:**
- If SQLModel reaches v1.0 with stable async + Alembic → consider migrating

### ADR-003 — Job Queue: ARQ

| Field | Value |
|-------|-------|
| **Date** | 2026-03-22 |
| **Status** | Accepted |
| **Deciders** | Brainstorm pipeline |

**Context:** Scraping jobs run 5-30 minutes. Need async job queue with progress reporting, retry, cancellation, and Redis backend.

**Decision:** ARQ (Asynchronous Redis Queue) — lightweight, Python-native, async-first.

**Alternatives Considered:**

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Celery | Most popular, mature, feature-rich | Synchronous by default, complex configuration, heavy dependency | Overkill for our use case, async support requires extra setup |
| Dramatiq | Simpler than Celery, good defaults | Synchronous, RabbitMQ preferred, smaller community | Our engines are async — need native async support |
| RQ (Redis Queue) | Simple, Redis-backed | Synchronous, limited features, no native async | Same async concern |

**Consequences:**
- Native async: workers can run crawl4ai without blocking
- Lightweight: ~500 lines of code, easy to debug
- Less mature than Celery — may need custom retry logic
- Redis is already needed for rate limiting — no new dependency

**Revisit When:**
- If we need complex workflow orchestration (DAGs, chains) → consider Celery or Prefect
- If job volume exceeds single-worker capacity → consider horizontal scaling with Celery

### ADR-004 — Authentication: API Key (Hashed)

| Field | Value |
|-------|-------|
| **Date** | 2026-03-22 |
| **Status** | Accepted |
| **Deciders** | Brainstorm pipeline |

**Context:** API service needs authentication. Users are developers integrating via SDK/curl, not humans logging into a web UI.

**Decision:** API key authentication with SHA-256 hashing. Keys have a visible prefix (`pk_` + first 8 chars) for identification, full key is only shown at creation time.

**Alternatives Considered:**

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| OAuth 2.0 | Industry standard, token refresh, scopes | Complex for API-only service, requires auth server, overhead for simple use cases | Too heavy for developer API — adds friction |
| JWT Tokens | Stateless, include claims | Need refresh mechanism, can't revoke without blacklist | API keys are simpler and better for long-lived integrations |

**Consequences:**
- Simple for developers: single header `Authorization: Bearer pk_xxx...`
- Keys never stored in plaintext — only hash + prefix
- No token expiry by default — keys valid until revoked
- Per-key rate limiting is straightforward
- No built-in scopes — all keys have full access (initially)

**Revisit When:**
- If enterprise customers need fine-grained permissions → add scopes to keys
- If we add a web dashboard → add OAuth/session auth for human users

## Data Flow

### Scraping Request Flow

```
1. Client sends POST /api/v1/scrape with URL + config
2. API validates request (Pydantic) and authenticates (API key)
3. Job created in PostgreSQL (status: "queued")
4. Job enqueued to ARQ (Redis)
5. API returns 202 Accepted with job ID
6. Worker picks up job, updates status to "running"
7. Worker invokes crawl4ai scraper (async)
8. Scraped pages → PostScraperCleaner → DocPostProcessor
9. Results written to file storage
10. Job updated to "completed" with result_path
11. If webhook URL provided → POST callback
12. Client polls GET /api/v1/jobs/{id} for status
13. Client downloads results via GET /api/v1/jobs/{id}/result
```

### Authentication Flow

```
1. User creates account (POST /api/v1/auth/register)
2. User creates API key (POST /api/v1/auth/keys)
3. Server generates random key, stores SHA-256 hash + prefix
4. Key shown ONCE to user (never stored in plaintext)
5. Client includes key in all requests: Authorization: Bearer pk_xxx...
6. API middleware extracts prefix, looks up hash, verifies
7. On match: request proceeds with user context
8. On failure: 401 Unauthorized
```

## Key Architectural Patterns

### Separation of Library and API

The core scraping/processing engines in `src/docscraper/` are a standalone Python library. The API layer in `api/` wraps them but never modifies them. This ensures:
- Library can be used without the API (CLI, scripts, GUI)
- API changes don't break library behavior
- Testing is layered: unit tests for library, integration tests for API

### Async-First Processing

All I/O operations are async:
- `crawl4ai.AsyncWebCrawler` for scraping
- `aiofiles` for file I/O
- `asyncpg` for database operations
- `ARQ` for job queue

### Job State Machine

```
QUEUED → RUNNING → COMPLETED
                 → FAILED
         RUNNING → CANCELLED (user-initiated)
```

## Security Architecture

### Attack Surface

| Vector | Risk | Mitigation |
|--------|------|------------|
| API Key Theft | HIGH | SHA-256 hashed storage, key rotation, revocation |
| SSRF via scraping | HIGH | URL allowlist (optional), domain validation, no internal IPs |
| Injection | MEDIUM | Pydantic validation, SQLAlchemy parameterized queries |
| Rate Limit Bypass | MEDIUM | Per-key limits (not per-IP), Redis-backed |
| Webhook Spoofing | MEDIUM | Stripe signature verification |
| DoS via large scrape | MEDIUM | Max pages limit, job timeout, queue depth limit |

### Data Classification

| Data Type | Classification | Encryption | Access |
|-----------|---------------|------------|--------|
| API Keys | Sensitive | SHA-256 hashed (never stored plaintext) | Owner only (prefix for identification) |
| User Email | PII | Encrypted at rest (PostgreSQL) | Authorized endpoints only |
| Scraped Content | User Data | Transit only (HTTPS) | Owner's API key only |
| Usage Records | Business | At rest + transit | Owner + admin |
| Stripe Tokens | Sensitive | Managed by Stripe | Never stored locally |
